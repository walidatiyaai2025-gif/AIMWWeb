# AIMWWeb 155.150.0 — Verified and idempotent PayPal webhook inbox

Canonical feature: `BIL-009`
Tracking issue: #148

## Delivered

- Added PayPal webhook ID configuration alongside the existing sandbox/live encrypted client credentials.
- Extended the PayPal gateway with `WebhookVerification` capability using PayPal postback verification at `/v1/notifications/verify-webhook-signature`.
- Verification requires the configured webhook ID, OAuth Bearer authentication, required PayPal transmission headers, trusted PayPal certificate URL, and the original webhook event payload.
- Only `verification_status=SUCCESS` can produce `GatewayVerifiedEvent` evidence.
- Added normalization for PayPal subscription lifecycle webhook types into the provider-neutral subscription state vocabulary.
- Added a durable verified-event inbox with case-normalized provider event identity, cross-provider deterministic uniqueness, replay-safe duplicate acceptance, and conflict rejection when the same event ID carries different normalized data.
- Raw provider bodies, access tokens, client secrets, and verification response bodies are not stored in the inbox.
- Added `/api/billing/paypal/webhook` as an anonymous provider callback endpoint with bounded body handling. Verified new and duplicate events return success; invalid messages are rejected and temporary verification/storage failures return service unavailable.
- Webhook intake never mutates `AccountSubscription`; subscription lifecycle synchronization remains the responsibility of BIL-010.
- Added SQLite migration `20260818202000_AddPayPalWebhookInbox`; non-SQLite installations continue to use provider-native generated DDL plus the existing missing-table upgrade planner.
- Added automated coverage for webhook ID configuration, postback verification request shape, SUCCESS/failure handling, event normalization, sanitized failures, durable replay idempotency, conflict detection, inbox migration, intake status, and zero subscription-state mutation.

## Boundaries

No subscription synchronization, plan changes, billing UI, raw webhook retention, or provider-state mutation is introduced in this release.

Final merge remains conditional on the exact PR head passing all required repository gates with zero unresolved review threads.
