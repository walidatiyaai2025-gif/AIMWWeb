# 155.142.0 — Durable execution-job failure email alerts

## Summary

Persisted failed `ExecutionJob` records can now be relayed to the affected site's configured notification recipients through the existing tenant-safe email outbox. This extends the operational-alert path introduced for WordPress synchronization failures without coupling email delivery to the original job lifecycle.

## Implemented

- Add the stable bilingual `site.job-failure` email template with site, job type, failure reason, occurrence time, correlation ID, and site URL tokens.
- Reuse explicit `OwnerUserId` + `SiteId` tenant identity and enabled site recipient resolution; no HTTP current-user dependency is introduced.
- Route alerts exclusively through `IEmailOutbox`; no direct SMTP send path was added.
- Derive deterministic idempotency and correlation from the persisted `ExecutionJob.Id`, preventing duplicate alerts across relay retries and restarts.
- Sanitize password/token/API-key/authorization assignments, bearer credentials, URL user-info, and line breaks; bound failure details and job labels before they enter the rendered email/outbox snapshot.
- Add a durable relay for persisted jobs whose status is `Failed`, plus a hosted worker with a 24-hour recovery window and isolated per-event retries.
- Preserve the existing WordPress synchronization-failure alert behavior while sharing common tenant, recipient, idempotency, sanitization, and outbox helpers.
- Add integration/regression coverage for tenant isolation, enabled/disabled/no-recipient behavior, duplicate suppression, Arabic rendering, secret redaction, persisted failed-job relay, completed-job exclusion, and template registration.
