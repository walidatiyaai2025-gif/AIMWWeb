# AI WordPress Manager 155.123.0

## Tenant-safe notification center
- The persistent notification inbox now stores authoritative owner, site, execution-job, read, dismiss, and source metadata.
- Existing SQLite notification databases are upgraded in place.
- Ownerless legacy notifications are preserved but are not exposed to a tenant.
- Read, mark-all-read, dismiss, and retention mutations are owner scoped.
- The legacy HTTP `userId` parameter can no longer select another user's inbox; authenticated identity is authoritative.

## Operational delivery
- Content Planner, bulk WordPress jobs, media operations, and approval lifecycle events write durable notifications for the relevant application owner.
- Background bulk work writes one final durable outcome instead of producing retry/item notification noise.
- Media and approval notifications carry site and Execution Center job correlation where available.
- Approval recipients are resolved from the current application Site owner rather than request display strings.

## UI
- `/notifications` reads the signed-in owner's inbox and supports dismiss.
- The header notification center uses the same persistent backend and links to the full inbox.
- Numeric notification severity values are mapped correctly in the header.
- Execution-job notifications route to Execution Center; media/planner sources route to their operational workspaces.

## Retention and failure semantics
- Read/dismissed notifications are retained for 90 days by default, with a bounded per-owner history policy.
- Cleanup cannot remove another tenant's notifications.
- Notification persistence is best-effort after authoritative operation state changes so notification-storage failure does not create false operational failure.

## Verification
- Added migration, tenant-isolation, read/dismiss, retention, restart-persistence, and HTTP identity-spoofing regression coverage.
- Full solution build and automated tests are required again on the final reconciled release head before merge.
