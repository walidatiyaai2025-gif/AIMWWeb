# AIWMWeb Laravel — تحديث النظام من لوحة الإدارة (#1400)

## الهدف
بعد نشر الإصدار الأول الذي يحتوي على هذه الميزة، يستطيع **مدير المنصة فقط** الدخول إلى
\`/admin/system-updates\` وفحص أحدث GitHub Release مستقر ومعتمد وتثبيته دون فتح cPanel في التحديثات العادية المتوافقة.

**لا يعني دمج PR نشر الموقع.** لا يوجد تحديث إنتاجي متاح حتى ضبط مفتاح التوقيع العام في الاستضافة ونشر حزمة معتمدة موقعة بالفعل.

## التهيئة الأولى لمرة واحدة (cPanel)
1. راجع وصوّر نسخة احتياطية **خارج ملفات التطبيق** لقاعدة البيانات وملف \`.env\` و\`storage\` و\`public/index.php\` وملفات الموقع.
2. انشر ميزة التحديث نفسها لأول مرة بآلية النشر الحالية بعد اجتياز CI ومراجعة الأمن ومراجعة استضافة cPanel.
3. تأكد من PHP 8.3+ والامتدادات \`sodium\` و\`zip\` وصلاحيات كتابة الملفات ونطاق \`public_path()\` الفعلي.
4. أنشئ زوج مفاتيح Ed25519 **خارج المستودع**، واحتفظ بالمفتاح الخاص في مخزن أسرار CI لإصدار الحزم فقط؛ لا ترفعه إلى cPanel.
5. ضع في بيئة Laravel على cPanel:
   \`\`\`dotenv
   AIWM_UPDATES_ENABLED=true
   AIWM_UPDATES_PUBLIC_KEY=<base64-ed25519-public-key>
   APP_VERSION=0.0.0
   \`\`\`
   استبدل APP_VERSION برقم النسخة الفعلي متى كان معروفًا. حافظ على APP_KEY كما هو. أعد تحميل config cache بأمان.
6. لا تنشر إصدارًا قبل نجاح الاختبارات المطلوبة على SHA المطلوب واعتماد النشر.

## إنشاء حزمة الإصدار على CI موثوق
بعد بناء Laravel dependencies لـ PHP الإنتاج و\`npm ci && npm run build\`، وبشرط نجاح CI على SHA النهائي، شغّل:
\`\`\`bash
AIWM_UPDATES_SECRET_KEY="<base64-ed25519-secret-key>" php variants/laravel-aiwmweb/tools/release/build-signed-update.php 1.0.1 <40hex-source-sha> /secure/output
\`\`\`
المخرجات الثلاثة المطلوبة بنفس الأسماء الثابتة:
- \`AIWMWeb-Laravel-release.json\` — إصدار وSHA وقائمة الملفات وSHA256 للحزمة.
- \`AIWMWeb-Laravel-release.sig\` — Ed25519 detached signature على بايتات JSON نفسها.
- \`AIWMWeb-Laravel-update.zip\` — ملفات backend المشمولة بالتوقيع.

انشر الملفات الثلاثة كـ assets في **أحدث GitHub Release مستقر وغير Draft** من مستودع \`walidatiyaai2025-gif/AIMWWeb\`. لا تنشر حزمة من branch غير مدمج أو فحوص ناقصة. لا تجعل سر التوقيع متاحًا لبناء PRs غير موثوقة.

## من لوحة الإدارة
1. ادخل بحساب \`platform_admin\`.
2. من Settings > System updates أو افتح \`/admin/system-updates\`.
3. اضغط Check for updates. يعمل فحص حي، ولا يعتمد على نسخة محفوظة أو على رقم غير موثق.
4. عندما تعتمد الإصدار، اكتب \`INSTALL\`، واضغط التثبيت. يتم إعادة الفحص والتوقيع والـ SHA256 في الطلب ذاته.
5. الخدمة تحجز lock، تنزل ZIP، تتحقق من كل ملف ومساره، تحفظ نسخ الملفات السابقة في \`storage/app/system-updates/backups/<id>\`، وتفعّل وضع الصيانة أثناء النسخ، تتحقق من hash لكل ملف وتُسجل إيصال الإصدار. عند فشل عملية الاستبدال تحاول استعادة النسخة السابقة وإلغاء وضع الصيانة.

## قيود أمنية وتشغيلية
- الواجهة لا تقبل URL يتحكم به المستخدم، ولا ZIP عشوائيًا. لا يمكن استخدام GitHub raw ZIP مباشرًا: يلزم توقيع منفصل صادر من مفتاح اعتماد محفوظ خارج الاستضافة.
- \`.env\` و\`storage\` و\`public/index.php\` و\`public/.htaccess\` ومسارات قاعدة البيانات غير قابلة للاستبدال من ZIP. ولا تُنفّذ أوامر DB migration أو Composer أو npm من طلب HTTP.
- قناة الإصدار الأولى **للتحديثات المتوافقة دون migrations**؛ الإصدارات التي تتطلب migrations مقيّدة حتى توفير تنفيذ مرحلي ونسخة DB/rollback واختبارات موثوقة. لا تستخدمها للتحديثات الكاسرة للمخطط.
- النسخ الاحتياطية لا تُحذف آليًا؛ راقب مساحة التخزين. في حال انقطاع PHP مفاجئ بين تحديث الملفات قد يلزم إصلاح يدوي باستخدام النسخة الاحتياطية.
- راقب صحة الموقع بعد كل إصدار، وراجع سجلات \`storage/app/system-updates/history.jsonl\`. نجاح النسخ للملفات لا يثبت وحده نجاح الوظائف المتكاملة أو النشر.
- **التثبيت على الموقع الفعلي غير منفذ هنا؛ GitHub يثبت الكود فقط.**
